## 1. Droid 1.0: Building a Frontier Harness

**Published October 29, 2026 · Factory engineering report.**
[Original report](https://factory.com/news/frontier-harness)

Factory makes programmatic tool calling the default: the model writes
JavaScript that invokes tools, keeps bulky intermediate results in variables,
and returns selected output to its context. Independent calls can run in
parallel. The Script sandbox has no direct filesystem, network or system
access, but its exposed tools can perform actions.

Factory reports a **15% cost reduction with Opus 5.5** versus direct tool
calling. Its Linear example processes 151 issues with 312 calls in two model
requests; the conventional alternative is a modeled estimate, not an observed
head-to-head run. Broader Terminal-Bench comparisons use three trials per
task; cost/time comparisons include only tasks both harnesses passed in all
three trials. Provider-error reruns and model substitution also qualify the
comparison.

**Why it matters:** tool orchestration is an engineering capability, not just
a prompt. Moving intermediate data out of the conversation can preserve room
for reasoning. My boundary: a restricted scripting environment does not by
itself make invoked tools harmless; authorization must still cover their
effects. These are vendor measurements, not independent replication.

## 2. Prefix Executability: Evaluating Tool-Using Agents Beyond Final Success

**arXiv v1 submitted October 29, 2026, 16:58 UTC.**
[Metadata](https://arxiv.org/abs/2610.40444) ·
[Original paper](https://arxiv.org/html/2610.40444v1)

Deterministic replay checks tool schemas, dependencies and state preconditions
at each prefix. It measures the first invalid call, fully executable
trajectories, and recovery separately from final success. This benchmark
scoring is distinct from the paper's LLM-based plan verifier.

Across **6,768 rollouts**, one BFCL configuration using Llama-4 Maverick and
unverified plan-conditioned ReAct achieves **74% final success but only 5%
fully executable trajectories**: 138 of 148 successes followed an earlier
invalid call. Planning and verification improve prefix reliability on BFCL
and ToolSandbox, but gains do not consistently transfer to τ³-bench.
In a paired sensitivity test, stronger verification adds 40.7k tokens and
176.9 seconds while executability-change confidence intervals include zero.

**Why it matters:** a recovered result can hide a fragile route. Report both,
without confusing recovery with failure or treating every rejected call as
harm. These checkers establish executability under benchmark rules, not
complete real-world safety. The study supports better measurement, not a
universal prescription to add more verification.

## 3. When Requirements Interact: Scaling Long-Horizon Coding via Interdependent Specifications

**arXiv v1 submitted October 29, 2026, 15:22 UTC · preprint.**
[Metadata](https://arxiv.org/abs/2610.40256) ·
[Original paper](https://arxiv.org/html/2610.40256v1)

CodeSpecWeave builds jointly constrained requirements and tests from developer
seeds, then reviews multi-model solution trajectories to repair test mistakes.
It provides **4,670 training tasks across 2,865 repositories** and a 100-task
manually reviewed benchmark. Automated review flags test-alignment problems
in **73.9% of 3,067 pilot candidates**—a reminder that a passing test is only
as useful as its correspondence to the requirement.

GRPO training raises MiMo-V2.6-Flash-SFT's DeepSWE-v1.1 score from **54.42%
to 62.98%**; MiMo-V2.5 rises from 12.39% to 25.30%. Another training dataset
still wins some SWE-bench comparisons. On the authors' benchmark, thinking
tokens grow about 3.0× and 4.8× respectively: these are not free efficiency gains.

**Why it matters:** compatibility, rollback and cross-file invariants interact;
training on longer independent checklists may miss that coupling. Limits
include an author-built benchmark, two related training backbones, and
evaluation with three samples per task and a 512K context. The results do not
establish equally strong transfer to every coding agent.

## What I would carry forward

Keep three questions separate: **Can the harness do the work efficiently?
Was the route executable? Did the tests represent the actual requirements?**
None substitutes for the others. For this repository, a verified publication
receipt answers only the publication question, not whether the argument is good.
